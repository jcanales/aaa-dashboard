2 · Business Rule — Per-Client Access Scoping

backend/src/api/entryScope.ts is the single source of truth for role-based row scoping against the legacy MSSQL tables. null = unrestricted (admin/broker); an array (possibly empty) scopes the caller to specific CO_KEYs.

Drift risk (confirmed live): aes.ts and abi.ts still define their own copy-pasted getAllowedCoKeys / assertCoKeyAllowed instead of importing the shared entryScope module — only entries.ts and htsBreakdown.ts were migrated in commit 66a68b1. Column names also differ per legacy table: USENTRY.CUST_KEY, EDI_FILES.IMPOR_KEY, TRAF.CUST_KEY, USDSTMT.IMP_KEY. A future fix to the scoping logic must be applied in four places unless consolidated.

3 · Business Rule — Chapter-99 Duty Bucket Classification

backend/src/api/htsBuckets.ts is the single source of truth for both the TypeScript classifier and the generated SQL predicates, used by every KPI/breakdown query that needs to split duty into Section 301 / Section 232 / IEEPA / other Chapter-99 buckets.

scroll
flowchart TD A["TUSA tariff number\n(from USLINE / USLINEB)"] --> B["Strip non-digits"] B --> C{"Starts with '99'?"} C -- No --> REG["regular\nordinary column-1 duty"] C -- Yes --> D{"Prefix ∈\n990388·990389·990391?"} D -- Yes --> SEC301["sec301"] D -- No --> E{"Prefix ∈\n990380·990381·990385·\n990376·990378·990379·990394?"} E -- Yes --> SEC232["sec232"] E -- No --> F{"Prefix ∈\n990301·990302?"} F -- Yes --> IEEPA["ieepa"] F -- No --> OTHER["other99\n(incl. 990303 border/fentanyl IEEPA order)"] classDef bucket fill:#dbeafe,stroke:#3A6FF9,color:#1e3a8a classDef warn fill:#fefce8,stroke:#ca8a04,color:#713f12 class REG,SEC301,SEC232,IEEPA bucket class OTHER warn
990303 is intentionally excluded from IEEPA: the legacy MSSQL header fields (USENTRY.DUTY_SEC_IEEPA) never count it there either, so classifying it as IEEPA would break reconciliation against the header totals.

Header-vs-line reconciliation: the per-line breakdown query (htsBreakdown.ts) treats header DUTY as authoritative for duty actually owed and excludes entries like type 23 (TIB) whose line duty was computed but never assessed — this closes the reconciliation gap to ~$95 on $18.35M of Q1 2026 duty (see task-3-report.md). Verified against 7,387 Q1-2026 entries.

4 · Business Rule — HTS Duty Breakdown Query Pipeline

GET /api/entries/hts-breakdown re-buckets every entry line (plus its Chapter-99 sub-lines) by commodity HTS code and duty type, for both the selected period and the equal-length prior period, so the frontend can render current-vs-prior comparison charts.

Stale-response guard: row expansion tracks a per-HTS fetch sequence number and a global filter-generation counter (expandSeq/genRef in DutiesBreakdownPage.tsx); an in-flight drill-down request whose generation has since changed (client/date filter changed mid-fetch) is discarded on arrival instead of overwriting newer state (fixed in 9537a2b).

5 · Business Rule — Tariff Change Intelligence Pipeline

Four cron pollers watch government sources for tariff-relevant publications. New content is classified by Claude, matched against client HTS portfolios, and queued for alerting — but nothing is sent until a licensed broker explicitly approves the change.

scroll
sequenceDiagram participant CRON as pollerManager (node-cron) participant POLL as Source poller\n(FR·CSMS·USITC·USTR) participant DIFF as sha256Differ participant PROC as changeDetector.processNotice participant AI as ☁️ Claude classifier participant DB as PostgreSQL (Prisma) participant MATCH as clientMatcher participant Q as alertQueue CRON->>POLL: scheduled tick (15m/20m/30m) POLL->>POLL: fetch source content POLL->>DIFF: sha256(content) DIFF-->>POLL: hasChanged(newHash, lastHash)? alt unchanged POLL-->>CRON: skip else changed / new document POLL->>PROC: processNotice(RawNotice) PROC->>AI: classifyTariffNotice(title, content) AI-->>PROC: {summary, impactScore 1-10,\nhtsCodes[], dutyBefore, dutyAfter} PROC->>DB: AiAuditLog.create (always, for audit trail) PROC->>DB: TariffChange.create (status = 'pending') PROC->>MATCH: matchClientsToChange(changeId) MATCH->>DB: Client.findMany({isActive: true, htsPortfolio}) loop each active client MATCH->>MATCH: htsCodesMatch(portfolioCode, changedCode)\n10-digit → 8-digit → 6-digit opt matched MATCH->>MATCH: calculateDutyImpact(annualValue, dutyBefore, dutyAfter) MATCH->>DB: ClientHtsMatch.create end end PROC->>Q: (via review flow later) queueAlerts(changeId) Q->>DB: Alert.create (status='queued') per client × channel end Note over DB,Q: Change sits in status='pending' until a broker reviews it. actor Broker as 👤 Broker / Admin Broker->>DB: GET /api/review (pending, sorted by impactScore desc) Broker->>DB: POST /api/review/:changeId {action: approved|suppressed} alt action = suppressed DB-->>Broker: status='suppressed' — no alerts ever sent else action = approved DB->>Q: queueAlerts(changeId) — idempotent DB->>Q: processApprovedChange(changeId) Q->>Q: 🔒 re-check status==='approved'\n(throws if not — non-bypassable) Q->>DB: Alert.findMany({status:'queued'}) loop each queued alert Q->>Q: send email or Slack Q->>DB: Alert.update({status: sent|failed}) end Q->>DB: TariffChange.update({alertsSent: true}) end
Non-bypassable gate: processApprovedChange throws if status !== 'approved'

8 · Database Schema — Legacy SQL Server (read-only)

The operational system of record for actual customs entries, lives outside this app. Duties Dashboard only issues scoped SELECTs against it — no writes. Connection config in backend/src/db/mssql.ts.

Inconsistent client-key column naming across legacy tables (CUST_KEY vs IMP_KEY vs IMPOR_KEY) is why the scoping helper can't be a single generic SQL fragment — see diagram 2.

Hardcoded credential fallback: backend/src/db/mssql.ts falls back to a literal server IP, DB name, username and password when the corresponding env vars are unset. This should be tightened (fail closed in production) rather than relying on env vars always being present.
